Microsoft Edge

Retokenizing a browser while the design system was still moving

How do you migrate an entire browser UI onto a new token system that is still being defined, without the browser changing appearance?

Role

Product Designer, audit owner

Company

Microsoft, 2024–

Scope

Shared components, then 50+ surfaces

Partners

~6 engineers

Duration

~1 year, audit to shipped tokens

Status

Tokens shipped, stable

Background

Edge's design files were built on Fluent. Edge's code was not. The two had never shared a token layer, so the interface people designed and the interface that shipped were described by different systems.

Microsoft was consolidating its products onto one design system — the same visual language across everything, and a browser built for the shift to AI. Edge could not join that until its interface was described in a vocabulary the system could speak.

The browser ships continuously, and midway through the work a new semantic token system arrived, bringing multiple themes with it. All of that was true at once, and it shaped every decision in this project.

The system we were adopting

MAIThe new system was Microsoft's shared semantic token set: one vocabulary of role-based tokens, with themes layered on top, so a product could take on a different appearance by changing what its tokens resolve to rather than by being redesigned.

I was part of that system's design group as well as Edge's adoption of it, which meant I saw both sides — what the system wanted to be in the abstract, and what a shipping product actually needed from it on a schedule. Nearly everything I contributed to the system came out of Edge: cases a browser has that the token set had not yet accounted for.

It was young. Names, structure and component-level tokens were all still settling while we were building against them, which is the constraint the rest of this project is a response to.

The problem

Themes were the goal, but you cannot theme what is hard-coded. Before any theme could exist, the browser had to stop referring to specific values and start referring to roles — and design and code had to be describing the same interface first.

  • Code shared no tokens with Fluent. The interface referenced colors directly. Fluent existed in Figma and nowhere in the codebase.
  • Design and production disagreed. The Figma files described a Fluent-based interface that was not what shipped, so neither side could be trusted as the source of truth.
  • The target changed mid-project. As we were preparing the code changes, the org adopted a new semantic token system, and it was still being defined while we moved onto it.
  • The scope was the whole browser. Not a component library in isolation — dozens of components across more than 50 surfaces, tied together by roughly 500 tokens.

Investigation

Reading the source

Edge is built on Chromium. Rather than audit the design files and hope they matched, I went into the codebase directly to find what the interface was actually made of. I ran that audit alone and documented every finding, and it took about two months.

That meant learning enough of the repository to know where interface values live, how they are referenced, and which layer a given color comes from. Edge also renders in two different worlds — native Views surfaces and WebUI surfaces — which do not share a styling mechanism, so a value had to be traced differently depending on where it lived.

It is a very large codebase and none of it is organised for a designer, but it was the only place the real answer existed.

Approach

Closing the gap in both directions

We were about to reconcile the code against Fluent when the semantic system landed. Rather than do the work twice, we changed target: redraw Edge in Figma on the new semantic tokens, and map those tokens to the values production was already shipping.

That meant redrawing a great deal of the browser in Figma — not to change how it looked, but to rebuild it out of tokens instead of raw values, so the design files finally described the same interface the code did, in the vocabulary both would use going forward. I was staffed as the audit's owner; the design team joined in on redrawing surfaces and mapping tokens together, while the line to engineering — making sure the right tokens actually landed in code — stayed mine.

The 1:1 mapping

The decision that made this shippable: every new semantic token was mapped so it resolved 1:1 to the appearance already shipping. The architecture underneath the browser changed completely. The browser looked exactly the same.

Migrate the plumbing invisibly first. Once every surface reads from a token, a new theme is a configuration change rather than a redesign.

Sequencing the rollout

I ordered the migration shared components first, surfaces second. The twenty or so general components — button, and its neighbours — account for most of what the browser is made of, so tokenizing them once moved a large fraction of the interface before any individual feature was touched.

Only then did we go surface by surface: favorites flyout, then the next one, across both Views and WebUI. By that point each surface was mostly assembled from parts that were already correct, and the remaining work was the handful of values specific to it.

Working with engineering

I worked directly with a partner team of about six engineers. Having read the source myself, I could talk about the change in terms of the files it touched and ask what was actually feasible, rather than handing over a spec and finding out later that it was not.

For each component we traced the shipped value back to the role it was playing and assigned the semantic token for that role. Where the system had no token for a case Edge needed, I defined one — and fed it back to the system owners, because a real product need is exactly what a young semantic set is missing.

It also made me the person engineers came to. A large share of the browser was being tokenized at once and plenty of features had no Figma at all, so when a team hit a value with no drawing behind it, the question came to me to resolve. The engineering lead thanked me for that specifically — which said more about where the bottleneck had been than any documentation could.

"Thank you for answering all the token questions for the things that didn't have Figma drawn."Partner engineering lead

The instability was the hard part. Before MAI there was another theme, Kumo, that we nearly adoptedAn earlier candidate theme was nearly adopted before the one we settled on, and component tokens in the new system kept changing underneath us. Engineering absorbed a steady trickle of small revisions as a result. The 1:1 mapping is what kept that trickle small: churn landed on names and references, never on how anything looked.

What tokenizing exposed

Assigning a semantic token forces you to say what a value is for. That question does not have an answer everywhere, and the places it did not were the interesting ones.

Reviewing surface after surface, I kept finding the same class of problem: one color doing two unrelated jobs, or two near-identical colors doing the same job on different surfaces. Nobody had decided those — they were the residue of values copied between files over years. A token cannot express "this gray, because the file next to it used this gray," so each one had to be resolved into an actual decision.

I kept those corrections separate from the migration and logged them as their own work. Folding them in would have broken the guarantee the whole project rested on: that nothing changed appearance. Held apart, they became a list of things worth fixing on purpose, with a reason attached to each.

Outcome

What shipped

The semantic tokens shipped. Edge's interface now reads from a semantic layer rather than from hard-coded values, and for the first time Figma and production describe the same system in the same vocabulary.

Then the swap actually happened. Edge shipped first on the Phoenix themethe first theme, which resolved to the appearance the product already had, and then moved to the MAI compact themethe shared system's compact theme — visually aligned to the shared Microsoft language, with the adjustments Edge's own surfaces needed. A change of that size, made by swapping what the tokens resolve to rather than by reopening every component. Deeper theming and additional themes beyond MAI are still working through canary and dev channels.

The swap also did something the mapping alone couldn't: it found bugs. Phoenix was close enough to the browser's existing look that a wrong token could hide in plain sight — a value that resolved to nearly the same pixel as before was never going to draw anyone's eye. MAI's bigger visual delta made those wrong assignments visible for the first time, in places that had shipped without complaint on Phoenix. None of it looked like a regression until the second theme arrived; it just looked like Edge.

The browser also simply looks more consistent than it did. Surfaces that had drifted apart over years now resolve from the same set of roles, so they agree by construction rather than by anyone remembering to check.

Reflection

The most useful thing I did on this project was read the code. Every plan built on the design files would have been a plan for a browser that did not exist, and no amount of care in Figma would have surfaced that.

The second was refusing to bundle a visual change into a structural one. It was tempting to fix the appearance and the architecture in a single pass. Keeping them apart is what made the work reviewable, and what let the project survive a specification that changed twice while we were building against it.

What I would carry forward: a migration that produces no visible difference can hide mistakes as easily as it hides risk. Phoenix's near-invisibility was the whole point of the approach, but it also meant a few wrong token assignments didn't surface until MAI's larger visual delta forced them into view, a year after they'd shipped quietly. Next time, I'd stress-test the mapping against a deliberately different theme earlier, instead of waiting for the first real theme swap to be the first real test.
