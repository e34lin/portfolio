Microsoft Edge

Retokenizing a browser while the design system was still moving

How do you migrate an entire browser UI onto a new token system that is still being defined, without turning the migration itself into a redesign?

Role

Product Designer, audit owner

Company

Microsoft, 2024–

Scope

Shared components, then 50+ surfaces

Partners

~6 engineers

Duration

~1 year, audit to shipped tokens

Status

Tokens shipped, stable

Background

Edge's design files were built on Fluent. Edge's code was not. The two had never shared a token layer, so the interface people designed and the interface that shipped were described by different systems, and the plan was to reconcile them.

Microsoft was moving its whole product line onto a new shared design system, a semantic token set meant to give everything the same visual language. Edge was also being positioned as the browser for the company's shift to AI, and it could not join the new system until its interface was described in the vocabulary it used.

The browser ships continuously, and that new system arrived partway through Edge's Fluent reconciliation work. It supported theming, but the themes themselves still had to be built.

The system we were adopting

The new system was Microsoft's shared semantic token set, one vocabulary of role-based tokens built to support theming, so a product could take on a different appearance by changing what its tokens resolve to rather than by being redesigned.

I was part of that system's design group as well as Edge's adoption of it, so I saw what the system wanted to be in the abstract and what a shipping product needed from it on a schedule, both at the same time. Nearly everything I contributed to the system came out of real problems Edge ran into, cases the token set hadn't accounted for yet.

It was young. Names, structure and component-level tokens were all still settling while we were building against them, which is the constraint the rest of this project responds to.

The problem

Themes were the goal, but you cannot theme what is hard-coded. Before any theme could exist, the browser had to stop referring to specific values and start referring to roles, and design and code had to be describing the same interface first. That problem was concentrated in Views. WebUI was already built with Fluent, but Views' native code was not.

  • Code shared no tokens with Fluent. The interface referenced colors directly. Fluent existed in Figma and nowhere in the codebase.
  • Design and production disagreed. The Figma files described a Fluent-based interface that was not what shipped, so neither side could be trusted as the source of truth.
  • The target changed mid-project. Partway through the code-to-Fluent reconciliation, the org adopted a new semantic token system, and it was still being defined while we moved onto it.
  • The scope was the whole browser. Dozens of components across more than 50 surfaces, not a component library in isolation.

Investigation

Reading the source

Edge is built on Chromium. The original task, component by component, was to find where Views' shipped code had drifted from its Fluent counterpart in Figma and work out what each one needed to change to close that gap. Instead of auditing the design files and hoping they matched, I went into the codebase directly to find what the interface was actually made of. I ran that audit alone and documented every finding, and it took about two months.

That meant learning enough of the repository to know where interface values live, how they are referenced, and which layer a given color comes from. Edge also renders in two different worlds (native Views surfaces and WebUI surfaces) that do not share a styling mechanism. WebUI's stylesheets already pointed at Fluent, which is why this particular audit was about Views.

It is a very large codebase and none of it is organised for a designer, but it was the only place the real answer existed.

The Fluent audit only covered Views, since WebUI already matched it. Once the new semantic tokens arrived, both halves needed tracing and replacing, just in two different ways depending on where a value lived.

What that tracing turned up:

Inconsistent even with itself

The same visual role could be hardcoded differently depending on which file happened to draw it. Nothing forced two components doing the same job to agree, let alone to agree with Fluent.

Drift, not redesign

Most of what shipped was already close to what Fluent specified. A handful of components had quietly wandered off it, sometimes for years, and nothing had caught it.

No mechanism to stay honest

Nothing connected the two, so any correction made in one place would drift out of the other again.

Approach

The 1:1 mapping

We were still reconciling the code against Fluent, one piece at a time, when the semantic system landed. Rather than close that gap once as a one-off patch and retokenize separately later, we combined the two, redrawing Edge in Figma on the new semantic tokens and mapping those tokens to the values Fluent had already specified.

This meant redrawing a great deal of the browser in Figma, rebuilding it out of tokens instead of raw values, so the design files finally described the same interface the code did, in the vocabulary both would use going forward. I was staffed as the audit's owner. The design team joined in on redrawing surfaces and mapping tokens together, while the line to engineering (making sure the right tokens actually landed in code) stayed mine.

Every one of roughly 500 new semantic tokens was mapped so it resolved 1:1 to what Fluent had already specified, not to whatever the code happened to be rendering at the time. That's the decision that made this shippable. In Figma, it produced no diff at all, since the redrawn files matched the original spec exactly. In production it did surface real differences, wherever code had quietly drifted from that spec. None of it amounted to a redesign. Primary actions were still blue, and the browser still read as Edge. The architecture underneath changed completely. What it looked like barely moved.

Map every token to what design already specifies, not to what's currently shipping. The gap between the two was already debt. The migration just collects it, once, on purpose.

Sequencing the rollout

I ordered the migration shared components first, surfaces second. The twenty or so general components (button and its neighbours) account for most of what the browser is made of, so tokenizing them once moved a large fraction of the interface before any individual feature was touched.

Only then did we go surface by surface, starting with the favorites flyout, then the next one, across both Views and WebUI. By that point each surface was mostly assembled from parts that were already correct, and the remaining work was the handful of values specific to it.

Working with engineering

I worked directly with a partner team of about six engineers. Having read the source myself, I could talk about the change in terms of the files it touched and ask what was feasible, instead of handing over a spec and finding out later it wasn't.

For each component we traced the shipped value back to the role it was playing and assigned the semantic token for that role. Where the system had no token for a case Edge needed, I defined one and fed it back to the system owners, because a real product need is exactly what a young semantic set is missing.

It also made me the person engineers came to. A large share of the browser was being tokenized at once and plenty of features had no Figma at all, so when a team hit a value with no drawing behind it, the question came to me to resolve. The engineering lead thanked me for that specifically, which said more about where the bottleneck had been than any documentation could.

"Thank you for answering all the token questions for the things that didn't have Figma drawn."Partner engineering lead

The instability was the hard part. An earlier candidate theme was nearly adopted before the one we settled on, and component tokens in the new system kept changing underneath us. Engineering absorbed a steady trickle of small revisions as a result. The 1:1 mapping kept that trickle small. Churn landed on names and references, never on how anything looked.

What tokenizing exposed

Assigning a semantic token forces you to say what a value is for. That question does not have an answer everywhere, and the places it did not were the interesting ones.

Reviewing surface after surface, I kept finding the same class of problem, like one color doing two unrelated jobs, or two near-identical colors doing the same job on different surfaces. Nobody had decided those. They were the residue of values copied between files over years. A token cannot express "this gray, because the file next to it used this gray," so each one had to be resolved into an actual decision.

I kept those corrections separate from the migration and logged them as their own work. Fluent hadn't settled these cases either, so there was no spec to map to, unlike the drift the audit had already resolved. Folding them in would have meant making real design decisions inside what was supposed to be a structural change. Held apart, they became a list of things worth fixing on purpose, with a reason attached to each.

Outcome

What shipped

The semantic tokens shipped. Edge's interface now reads from a semantic layer rather than from hard-coded values, and for the first time Figma and production describe the same system in the same vocabulary.

Then the swap actually happened. Edge shipped first on the first theme, which resolved to what Fluent had already specified and closed the drift the audit had found, without amounting to a redesign. It then moved to the shared system's compact theme, visually aligned to the shared Microsoft language, with the adjustments Edge's own surfaces needed. A change of that size, made by swapping what the tokens resolve to rather than by reopening every component. Deeper theming and additional themes are still working through canary and dev channels.

Because the first theme did move real pixels, even if modestly, we didn't just trust the mapping and ship it. Several experiment flights ran before the wide rollout, checking that the change read as neutral or positive rather than as a regression.

The swap also did something the mapping alone couldn't. It found bugs. The first theme was close enough to the browser's existing look that a wrong token could hide in plain sight. A value that resolved to nearly the same pixel as before was never going to draw anyone's eye. The second theme's bigger visual delta made those wrong assignments visible for the first time, in places that had shipped without complaint on the first theme. None of it looked like a regression until the second theme arrived. It just looked like Edge.

The browser also simply looks more consistent than it did. Surfaces that had drifted apart over years now resolve from the same set of roles, so they agree by construction rather than by anyone remembering to check.

Reflection

One of the most useful things I did on this project was read the code. Every plan built on the design files would have been a plan for a browser that did not exist, and no amount of care in Figma would have surfaced that.

The second was being precise about which visual changes belonged inside the structural one. Correcting drift against a spec Fluent had already settled was fair game, since that was debt already owed and the architecture change was the moment to pay it. Cases with no single correct answer, where nothing had been decided yet, were a different kind of change, and folding those in too would have smuggled real design decisions into what was supposed to be a structural pass. Keeping that line clear made the work reviewable, and let the project survive a specification that changed twice while we were building against it.

A migration that stays this close to what's already there can hide mistakes as easily as it avoids risk, and that's what I'd carry forward. Folding the Fluent correction into the architecture change kept its footprint small on purpose, but that also meant a few wrong token assignments didn't surface until the second theme's larger visual delta forced them into view, a year after they'd shipped quietly. Next time, I'd stress-test the mapping against a deliberately different theme earlier, instead of waiting for the first real theme swap to be the first real test.
