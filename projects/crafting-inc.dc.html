Crafting Sandbox

A single-machine interface for cloud dev environments

How can we develop a solution for single machine developers without disrupting our current multi-service customer base?

Role

Product Designer

Company

Crafting Inc.

Timeline

1–2 months, shipped 2024

Surface

Web app

Background

Crafting Sandbox gives developers a full development environment in the cloud for their multi-service apps. I worked on this for about two months.

Research

The problem

The existing sandbox was built for multi-service work. Engineers used to developing on a single machine found it confusing and slow to work in.

Initial problem discovery

  • The transition was hard. Engineers coming from single-machine setups got lost moving into a sandbox environment.
  • Sandbox or workspace? Nobody was clear on the difference between the two.
  • VMs everywhere. A lot of companies were already on VM-based setups, which made the move harder.
  • The UI worked against them. Single-machine users found the existing interface counterintuitive.

Key insights from user interviews

Single-machine users

Wanted a simpler interface with less in it.

Multi-service users

Needed deep configuration options and the ability to run a lot at once.

The overlap

Plenty of usability fixes would help both groups, with nothing traded away.

Design

Trade-offs discussed

Customization vs. Standardization

How much personalization to allow before the platform stops feeling uniform and predictable.

Simplicity vs. Functionality

Single-machine users wanted it simple. Multi-service users needed it powerful.

Speed vs. Comprehensive Features

Keeping it fast and light while still carrying everything advanced users depend on.

Proposed solution

Direction chosen

Configurable Interface Design

Let people switch between single-machine and multi-service environments freely.

Pro
People can tailor their workspace without touching anything multi-service users depend on, so single-machine support lands without breaking what already works.
Con
It adds a second interface to learn. Switching between them is one more thing to figure out, which could slow people down at first.

Design principles

Simplicity in Design

Both interfaces had to be easy to move between. That meant clear labels, the same visual elements in each, and a toggle that didn't make anyone stop and think.

User-Centric Adaptability

The interface had to flex for different people and skill levels. Settings they could adjust to fit their own workflow, and a way to send feedback so it kept improving.

Consistency Across Environments

The same elements and patterns in both interfaces. If the core concepts stay familiar, switching modes costs almost nothing.

User journey

The point of this journey was to make sure people knew both options existed, and that each one suited a different kind of work.

We walk people through what the Single Workspace UI and the Full Web UI each do well, then help them pick the one that fits the project in front of them.
