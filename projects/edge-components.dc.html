Microsoft Edge

Deciding what a browser should carry

Design system work on Edge, all of it circling one question. Which parts of this interface should be ours to maintain, and which shouldn't?

Role

Product Designer, design systems

Duration

2024 – present

Team

5 designers

Layer

20–25 components

The thread

Edge is built on Chromium and sits on a shared Microsoft design system, so most of its interface is inherited. The design work that matters is deciding which parts shouldn't be.

Three pieces of work with the same question underneath. Some components Edge has no choice but to own, because nothing upstream will ever build them. Others Edge had been carrying for years without needing to, at a cost that came back every release. And illustration sat with one person, which is its own kind of ownership problem.

All three come down to the same call. What should this team be responsible for, and what should it stop being responsible for?

What Edge must own

A shared design system is general by definition. It carries what every product has in common, things like buttons, inputs and menus, and stops there. For a browser, what's left over is most of the interface. The address bar, the profile control, the side panel, all the surfaces a browser puts around a page. None of them exist in a general system and none of them ever will.

So Edge keeps its own component layer on top of the shared one, twenty to twenty-five components, each with its own sub-components, states, sizes and per-feature variants. A team of five designers owns it. I built and maintain five to ten.

Owning it well

Rebuilding from the product

The components were not designed from a blank canvas. I recreated each one from what the product was rendering at the time, then rebuilt it on semantic tokens.

That order matters. If a component library describes an improved version of the product, engineering can't adopt it without shipping a redesign at the same time, which makes it a proposal instead of a system. Rebuilding from what shipped meant the layer could be picked up right away, and improvements could come after, one at a time, with everyone able to see exactly what changed.

Describe the product as it is before describing the product as it should be. Otherwise the library and the browser drift apart on day one.

Working this way turns up how much of an interface was never decided in the first place. A component in code has whatever states someone needed at the time. A component in a library has to declare all of them. Most of the inconsistency in a mature product lives in the gap between those two.

So a lot of rebuilding each component was closer to counting than to designing. I listed every state, size and variant the component owed, then worked out which ones existed, which existed but differed from surface to surface, and which had never been drawn at all and were just whatever the code happened to produce.

The undrawn ones were the point. Nobody had chosen them, so nobody was following them, and no two surfaces had to agree. Specifying them didn't change how the browser looked in the common case. It changed how many ways the uncommon cases could go.

Maintaining a live layer

The layer is not a project with an end. The browser keeps shipping, and the shared system underneath keeps moving, so the work is continuous.

  • New variants as features ship. Every new feature wants something the component doesn't do yet. Deciding whether that's a variant, a new component, or a request the feature should drop is the recurring judgment.
  • Keeping step with the system underneath. The shared system changes its own tokens and components, and the Edge layer has to absorb that without breaking what's built on it.
  • Reviewing how other designers use it. Components get used in ways they weren't designed for. Catching that early is cheaper than the pattern spreading.
  • Deprecating and consolidating. Old patterns accumulate. Removing one means finding every use of it and giving each a replacement.
  • Behaviour at every window width. A browser gets resized constantly, so components have to be specified across the full range, not at one canvas size.

Owning less

What Edge stopped owning

The other half of the question. Over the years Edge had diverged from Chromium in a lot of small places, features where Edge's version looked or behaved differently for no reason that held up. Each of those differences is a patch the team carries forever, re-applied, re-tested, and occasionally re-fixed every time upstream moves. The cost doesn't end when the feature ships.

Reducing that divergence is a standing direction from leadership. Every patch retired is engineering time back in the team's hands, spent on features instead of maintenance. The work lands on me a feature at a time, energy saver, the performance detector, picture-in-picture, media controls, toast notificationsenergy and performance surfaces, media and notification controls among them.

Alignment doesn't mean becoming Chromium. Edge can't ship upstream's interface literally, since it has its own components, tokens and brand. So each feature gets edgeified. Take upstream's structure and behaviour, then rebuild the surface out of Edge's own system. Same shape underneath keeps the patch thin and cheap to carry. Edge's own appearance on top means nothing about it reads as borrowed.

In practice that means digging into what upstream actually does, working through with the PM which parts of Edge's version were load-bearing and which were habit, resolving the difference into Edge's components, and handing the result to engineering. The judgment is in the middle step. Most of what looked like a deliberate Edge decision turned out to be an accident nobody had revisited.

One case in detail

Edge's performance detectorOne of Edge's performance surfaces watches for conditions that might be slowing the browser down and badges the toolbar to recommend an action. It arrived as part of a wider Edge-only hub that gathered the performance and safety features in one place. That hub underperformed and was later folded down into a single performance surface.

<1%

Clickthrough among monthly active users. Effectively nobody was acting on it.

Badges ≫ actions

A large gap between how often the badge appeared and how often anyone did anything about it.

That gap says something more specific than "low usage." Two things were wrong at once. The interface wasn't persuading anyone, and the heuristic behind it was firing when there was nothing worth acting on. A badge that is usually wrong teaches people to ignore it, and then it fails even in the cases where it's right.

That made the decision straightforward. Redesigning the badge would have made an untrusted signal more prominent without making it more useful, and Edge would have kept paying to maintain its own version either way. Aligning to upstream removed the patch, put the feature on a pattern everyone maintains, and left the underlying heuristic as the problem it had been all along.

Designers aren't usually the ones raising maintenance cost in a review. Being able to say what a difference costs the team every release, not just what it looks like, kept these conversations short.

Spreading ownership

What nobody owned

Illustrations were the one part of the interface with no system at all. Every one was a one-off, and the creative director drew all of them, so the ownership sat with one person instead of in a system.

That produced two problems at once. The set was inconsistent, because nothing defined the frame or the style, and the creative director was a bottleneck on every feature that needed an image.

I wrote a guideline that gives designers a shared frame and style to work in, so they can get to a usable baseline themselves and hand that to the creative director to refine instead of originate. It changed the shape of the request. Designers now bring a draft and ask for an opinion instead of asking for an illustration. The creative director went from drawing every one to editing them, and the set had a common foundation for the first time. Edge's product designers use it, and so do the marketing teams, who have since built marketing video work on it as well as in-product illustration.

Outcome

Reflection

The useful contribution was rarely the drawing. It was deciding what should be a component and what shouldn't, which differences from upstream were worth their permanent cost, and what other people should be able to make without me.

The argument that carried the alignment work was never a visual one. A difference nobody could justify is engineering time spent every release keeping it alive, time that buys nothing and could be buying features instead. Put that way, a design proposal made sense to the people who fund the work.

Design systems work usually gets described as adding. More components, more coverage, more documentation. Most of what was valuable here went the other way, removing a difference nobody could justify, retiring a pattern, taking work off one person's desk. A smaller thing to maintain was worth more than a bigger thing to show off.
